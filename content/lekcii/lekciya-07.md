## 1.1.2.2 Классификация типов данных C++ (окончание)

### Как писать `&` и `*` в объявлении ссылки и указателя

Пробелы между именем типа, амперсандом или звёздочкой и именем переменной ни на что не влияют — для компилятора все три записи полностью одинаковы:

- `int& ref = a;`, `int & ref = a;` и `int &ref = a;`;
- `int* ptr;`, `int * ptr;` и `int *ptr;`.

Выбор формы — вопрос стиля, а не языка, но у каждой своя логика чтения. На практике эти стили распределяются так.

**Ссылки:**

- `int& ref = a;` — самый популярный стиль в C++. Он подчёркивает, что `int&` (ссылка на `int`) — это единый тип данных переменной `ref`. Именно эту форму требует Google C++ Style Guide: пробел перед амперсандом там прямо запрещён, пример руководства — `const std::string& str;`. Её же требуют стиль кода курса (п. 5c, см. 0.8 «Основы Code Style») и настройка `ReferenceAlignment: Left` в конфиге `.clang-format` лабораторных работ. Используется в тексте ранее, для знакомства.
- `int &ref = a;` — тоже частый стиль. Его обычно выбирают программисты, пришедшие из языка C, или те, кто предпочитает одинаковое оформление для указателей (`*`) и ссылок (`&`). Так принято в Qt — `const QString &myString = str;` — и в стиле ядра Linux. В курсе эта форма не используется: п. 5c выбирает вариант выше.
- `int & ref = a;` — встречается редко. Обычно его избегают, так как он делает код менее компактным и визуально «отрывает» знак ссылки и от типа, и от имени переменной.

**Указатели:**

- `int* ptr;` — самый популярный стиль в C++, его предпочитал Б. Страуструп (см. раздел «Is `int* p;` right or is `int *p;` right?»). Б. Страуструп отмечает: «типичный программист на C++ пишет `int* p;` и читает это как «`p` — указатель на `int`», подчёркивая тип». Тип читается целиком, слева от имени. Эту форму требует Google C++ Style Guide — `char* c;`, `int* GetPointer();`, — и её же закрепляет стиль кода курса (п. 5c, см. 0.8 «Основы Code Style»): в конфиге `.clang-format` лабораторных работ стоит `PointerAlignment: Left`, поэтому форматировщик приведёт объявления к ней автоматически.
- `int *ptr;` — тоже частый стиль: объявление повторяет использование — выражение `*ptr` имеет тип `int`. По тому же источнику, так пишет «типичный программист на C», подчёркивая синтаксис: в грамматике языка `*` действительно связана с именем `p`. Так принято в языке C, в стиле ядра Linux и в Qt — `char *x;`, а форматировщик Qt настроен как `--align-pointer=name`. В курсе эта форма не используется — п. 5c следует здесь не за Qt, а за Google; это единственное расхождение стиля курса с соглашениями Qt.
- `int * ptr;` — встречается редко и по той же причине, что и `int & ref = a;`. Но такие проекты есть: стиль ClickHouse требует именно пробелов с двух сторон — `const char * pos`, `const std::string & s`. В курсе эта форма появляется только там, где иначе запись читается тяжело, — `const char * const tmp = "hello";`.

Смешивать формы в одном файле нельзя: читателю кода важна предсказуемость, а не конкретный вариант.

> [!danger] Звёздочка и амперсанд действуют на одно имя, а не на весь список
> ```cpp
> int* ptr1, ptr2;        // ptr1 — указатель, а ptr2 — обычный int!
> int *ptr3, *ptr4;       // два указателя: звёздочка нужна каждому имени
>
> int& ref1 = a, ref2 = a;   // ref1 — ссылка, а ref2 — независимая копия типа int
> int &ref3 = a, &ref4 = a;  // две ссылки: амперсанд тоже нужен каждому имени
> ```

### Тип переменной: `*` и `&` — часть типа

> [!question]- Спецификатор `decltype` и свойства типов
> `decltype(выражение)` компилятор заменяет настоящим типом этого выражения, а само выражение не вычисляет. Здесь достаточно того, что `decltype(ptr)` — это тип переменной `ptr`; точные правила вывода разбираются в 2.2 доп. «`auto`, `decltype` и `decltype(auto)` — повышенный уровень».
>
> **Свойства типов (type traits)** — шаблоны из заголовка `<type_traits>`, которые на этапе компиляции отвечают на вопросы о типе или строят из него новый тип. Имя с окончанием `_v` — это `bool`-значение («является ли…»), с окончанием `_t` — сам тип-результат.
>
> ```cpp
> std::is_same_v<int, int>             // true  — в точности тот же тип
> std::is_same_v<int, const int>       // false — const входит в тип
> std::is_integral_v<char>             // true  — целочисленный
> std::is_integral_v<double>           // false
> std::is_pointer_v<int*>              // true
> std::remove_const_t<const int>       // int   — «снять» const с типа
> ```
>
> Ничего из этого в готовую программу не попадает: значения вычисляет компилятор, поэтому их подстановка происходит на этапе компиляции. <!-- TODO: конец фразы на фото обрезан -->

> [!example] Пример 1.14 — `*` и `&` как часть типа
> ```cpp
> int value = 42;
> int* ptr = &value;    // указатель
> int& ref = value;     // ссылка
>
> static_assert(std::is_same_v<decltype(value), int>);    // сама переменная — int
> static_assert(std::is_same_v<decltype(ptr),   int*>);   // указатель на int
> static_assert(std::is_same_v<decltype(ref),   int&>);   // & — часть типа, а не «просто имя»
> static_assert(std::is_same_v<decltype(*ptr),  int&>);   // разыменование даёт тот же int
>
> static_assert(sizeof(ptr) == sizeof(void*));  // 8 — размер адреса
> static_assert(sizeof(ref) == sizeof(int));    // 4 — размер объекта, не «ссылки»
> ```

Здесь спецификатор типа `decltype(x)` даёт тип выражения `x` (C++11) — компилятор подставляет вместо него настоящий тип, а само выражение не вычисляется (см. выноску выше). Переменная-шаблон `std::is_same_v<A, B>` из `<type_traits>` имеет `bool`-значение, вычисляемое компилятором, оно истинно, когда `A` и `B` — один и тот же тип. Программа собирается — значит, все шесть утверждений верны.

Что из этого стоит запомнить: `*` и `&` — **часть типа переменной**, а не украшение имени, поэтому типы `ptr` и `ref` удобно записывать как `int*` и `int&`. Оговорка одна, и она касается объявлений с несколькими именами через запятую, — см. выноску выше. Размеры подтверждают разную природу этих типов: указатель хранит адрес и занимает 8 байт на 64-битной платформе, а `sizeof(ref)` даёт размер самого объекта — ссылка не добавляет к нему ничего своего.

### Массивы

> [!abstract] Массив (array)
> набор из фиксированного числа элементов одного типа, расположенных в памяти подряд; объявляется как `тип имя[количество]`.

Массив — простейший способ хранить много однотипных значений под одним именем. Количество элементов задаётся при объявлении, входит в тип массива и не меняется во время работы программы. Обращение к элементу — по **индексу** в квадратных скобках, причём нумерация начинается с нуля: у массива из `N` элементов допустимы индексы от `0` до `N - 1`. Например, `int array[5]` и `int array[10]` — разные типы.

Расположение элементов подряд даёт массиву **прямой (произвольный) доступ**: адрес элемента вычисляется по индексу арифметически, поэтому обращение к `array[0]` и к `array[999]` занимает одинаковое время — перебирать промежуточные элементы не требуется.

> [!warning] Пропуск
> «Пример 1.15 — Массив» и «Пример 1.16 — Количество элементов массива» на снимках не поместились целиком. Дозаписать с новых фотографий.

Массив занимает ровно `количество * sizeof(элемент)` байт, а переход к следующему элементу — это сдвиг на один размер элемента.

> [!tip] Идиома `sizeof(массив) / sizeof(массив[0])`
> Пока в языке не было `std::size` (до C++17), количество элементов вычисляли делением: размер всего массива в байтах делят на размер одного элемента — см. Пример 1.16. Идиома удобна тем, что не зависит от типа элемента: поменяется `int` на `double` — формула останется верной.
>
> Но работает она **только там, где виден сам массив**. Если передать массив в функцию, то он затухает в указатель (см. пояснение ниже), и деление даст размер указателя, делённый на размер элемента, например `8 / 4 == 2`. Компилятор предупреждает об этом (`-Wsizeof-pointer-div`), но ошибкой не считает — программа соберётся и молча посчитает не то.
>
> В современном коде вместо этой формулы пишут `std::size(marks)` из заголовка `<iterator>` (C++17): считает то же самое, но при затухании массива просто не скомпилируется — ошибка обнаружится сразу.

Выход за границы массива компилятор не контролирует: программа <!-- TODO: начало абзаца на фото обрезано --> не сообщит об ошибке, а прочитает или испортит чужую память. Ошибка на единицу в границе цикла (`i <= N` вместо `i < N`) — одна из самых частых причин таких дефектов.

**Связь имени массива с указателями.** В большинстве выражений имя массива автоматически превращается в указатель на его первый элемент — это называют *затуханием* массива (array-to-pointer decay). Именно поэтому массив и указатель так часто соседствуют, а к указателю применима адресная арифметика: `ptr + 1` даёт адрес следующего элемента.

> [!abstract] Затухание массива (array-to-pointer decay)
> автоматическое неявное преобразование выражения типа «массив из `N` элементов типа `T`» в указатель на первый элемент этого массива (тип `T*`); выполняется компилятором, без каких-либо указаний в коде — в частности при передаче массива в функцию и при присваивании его указателю.

## 1.1.2.3 Литералы

С лексемой-литералом мы встречались в примере 1.1 при разборе инструкции `int count = 10;` в [[lekciya-02#1.1.1.2 Алфавит, лексика, синтаксис и семантика языка C++|1.1.1.2 «Алфавит, лексика, синтаксис и семантика языка C++»]] — теперь, зная типы (см. [[lekciya-04|1.1.2.1 «Фундаментальные типы данных C++»]]), можем сказать о литералах главное: каждый литерал имеет тип, и тип этот определяется самой формой записи.

> [!abstract] Литерал (от англ. *literal* — «буквальный»)
> запись конкретного значения непосредственно в тексте программы; тип литерала определяется формой его записи: `42` — `int`, `7.5` — `double`, `'a'` — `char`.

Литерал — это фиксированное значение: изменить его нельзя, ссылаться на него как на переменную — тоже. В стандарте ISO C то же понятие называется «константой», поэтому в литературе термины «литерал» и «константа» нередко используются взаимозаменяемо: в записи `const int n = 5;` значение `5` — целочисленный литерал.

Стандарт делит литералы на категории:

- литерал нулевого указателя `nullptr`,
- логические,
- целочисленные,

### `NULL` и `nullptr`

`NULL` — это **макрос** (см. [[lekciya-03#1.1.1.5 Библиотеки и заголовочные файлы|1.1.1.5 «Библиотеки и заголовочные файлы»]]), унаследованный из языка C. Разберём это по частям:

- **не литерал** — макрос есть текстовая подстановка: препроцессор заменяет имя `NULL` его текстом ещё до начала компиляции, поэтому своего типа у `NULL` нет; тип будет у того, что подставилось;
- **что подставится** — стандарт C++ конкретной записи не называет, он лишь требует, чтобы это была «константа нулевого указателя»: на практике `0`, `0L` или, в новых реализациях, `nullptr`. Например, в libc++ (Clang) `decltype(NULL)` даёт `long`, то есть `NULL` там — обычное целое число `0L`. Отсюда и неоднозначность при перегрузке (Пример 1.6 в [[lekciya-04|1.1.2.1 «Фундаментальные типы данных C++»]]): число одинаково подходит и функции для `int`, и функции для указателя;
- **`(void*)0` — константа нулевого указателя (используется в C, но не в C++)** — целочисленное константное выражение со значением 0, приведённое к типу `void*`; в языке C указатель `void*` неявно преобразуется в указатель любого типа, поэтому определение `NULL` как `(void*)0` там работает: строка `int* ptr = (void*)0;` компилируется. В C++ такого неявного преобразования нет — та же строка даёт ошибку `cannot initialize a variable of type 'int *' with an rvalue of type 'void *'`, понадобился бы явный `static_cast<int*>`. Значит, в C++ такое определение сделало бы `NULL` непригодным для присваивания указателям, и реализации определяют его иначе.

> [!info] Как на самом деле определён `NULL`
> Посмотреть на определение макроса можно прямо в заголовочном файле компилятора. У Clang это файл `__stddef_null.h`, который подключается через `<cstddef>`:
>
> ```cpp
> #ifdef __cplusplus
> #if !defined(__MINGW32__) && !defined(_MSC_VER)
> #define NULL __null
> #else
> #define NULL 0
> #endif
> #else
> #define NULL ((void*)0)
> #endif
> ```
>
> Это первая встреча с **условной компиляцией**: директивы `#ifdef` / `#if` / `#else` оставляют в тексте программы только одну ветку, остальные препроцессор отбрасывает до начала компиляции (директивы препроцессора — отдельная тема, см. 07 7.3 «Директивы препроцессора»). Макрос `__cplusplus` определён, когда файл обрабатывается как C++ <!-- TODO: конец выноски на фото обрезан -->

### Целочисленные литералы

Рассмотрим целочисленные литералы и литералы с плавающей точкой. Как видно из таблицы, тип литерала уточняется **суффиксом**: `10u` — `unsigned int`, `10L` — `long`, `3.14f` — `float`. Без суффикса целочисленный литерал — всегда `int`, дробный литерал — всегда `double`.

Полный перечень форм записи — в документации: «целочисленные литералы», «литералы с плавающей точкой», а также урок о литералах на learncpp.com.

Суффиксы целочисленных литералов можно комбинировать, порядок букв не важен, буквы суффиксов можно писать в любом регистре:

- `u` / `U` — беззнаковый: `42u` — `unsigned int`;
- `l` / `L` — длинный: `42L` — `long int`;
- в сочетании: `42uL` — `unsigned long int`;
- `ll` / `LL` (C++11) — очень длинный: `42LL` — `long long int`;
- `42uLL` — `unsigned long long int`;
- `z` / `Z` (C++23) — тип размера: `42uz` — `std::size_t`, `42z` — соответствующий ему знаковый тип.

Одно и то же число 42, записанное как `42` и `42L`, — литералы разных типов; дробное `7.5` и `7.5f` — тоже. А последняя строка примера показывает родство `bool` с целыми числами: `true` печатается как `1` (почему — см. классификацию интегральных типов в [[lekciya-04|1.1.2.1 «Фундаментальные типы данных C++»]]).

> [!tip] Замечания из документации
> - Регистр букв в литерале не значим: `0xDeAdBeEfU`, `0XdeadBEEFu` и `0xDEADBEEFu` — одно и то же число.
> - Единственное исключение — суффикс `ll`: обе буквы должны быть в **одном** регистре (`ll` или `LL`, но не `lL` и не `Ll`).
> - **Отрицательных целочисленных литералов не существует.** Запись `-1` — это литерал `1`, к которому применён оператор «унарный минус» (об операторах — параграф 1.2.3 «Инструкции выражения» темы 1.2).

Отдельный вопрос — что будет, если записанное число не помещается в тип, который полагается литералу по умолчанию. Компилятор не обрезает значение: он идёт по списку допустимых типов и берёт первый, в который число помещается.

- Для **десятичного** литерала без суффикса список такой: `int` → `long int` → `long long int`.
- Для **восьмеричных** (начинаются с 0) и **шестнадцатеричных** (с 0x) — список чуть шире, так как они чаще используются для битовых масок: `int` → `unsigned int` → `long int` → `unsigned long int` → `long long int` → `unsigned long long int`.
- Если значение слишком велико даже для последнего из них (максимум знакового `long long int` — примерно 9 · 10¹⁸), компилятор вправе использовать расширенный целочисленный тип (например, `__int128`), а если и такого нет — программа считается некорректной (ill-formed). Это значит, что код даже не скомпилируется, и вы получите ошибку компиляции.

> [!tip] Ловушка самого маленького `int`
> Правило об отсутствии отрицательных литералов — не формальность. Запись `-2147483648` компилятор читает как унарный минус, применённый к литералу `2147483648`, а это число в `int` уже не помещается (максимум — 2147483647), поэтому литерал получает следующий подходящий тип: на 64-битной платформе `long`. Убедиться можно оператором `sizeof`: `sizeof(-1)` даёт 4 байта, а `sizeof(-2147483648)` — 8.
>
> Присваивание `int x = -2147483648;` при этом работает — итоговое значение в `int` помещается, — но по дороге выражение успевает побывать более широким типом. Именно поэтому в заголовочном файле `<climits>` минимальная граница определена обходным путём: `#define INT_MIN (-2147483647-1)` — здесь оба литерала помещаются в `int`, и расширения типа не происходит.

Целочисленный литерал можно записать не только в привычной десятичной системе счисления, но и в двоичной, восьмеричной, шестнадцатеричной — форму записи выбирает программист.

> [!example] Сниппет 1.18 — Инициализация переменных одним и тем же значением
> Все пять переменных получают одно и то же значение 42 — литералы различаются только системой счисления:
>
> ```cpp
> int d = 42;         // десятичная запись
> int o = 052;        // восьмеричная: префикс 0
> int x = 0x2a;       // шестнадцатеричная: префикс 0x
> int X = 0X2A;       // то же самое: префикс и цифры нечувствительны к регистру
> int b = 0b101010;   // двоичная: префикс 0b (с C++14)
> ```

Все пять литералов имеют тип `int` и значение 42. Обратите внимание на ловушку восьмеричной записи: **ведущий ноль меняет значение** — `052` это 42, а не 52. И попутное наблюдени<!-- TODO: конец абзаца на фото обрезан, дальше ссылка на 1.1.2.4 «Имена» -->

### Литералы с плавающей точкой

Без суффикса дробный литерал имеет тип `double`; суффикс `f` / `F` делает его `float`, а `l` / `L` — `long double` (см. Таблицу 1.6).

Записать дробное число можно двумя способами:

- первый — привычная запись с точкой: `7.5`, `0.001`; одну из частей числа можно опустить — `.75` означает 0.75, а `2.` означает 2.0 (обе записи корректны и дают `double`, но в курсе предпочтительна полная форма: `0.75` и `2.0` читаются однозначно, а потерянный ноль легко принять за опечатку);
- второй — **экспоненциальная форма** (scientific notation), повторяющая научную запись числа: буква `e` (или `E`) отделяет мантиссу от показателя степени десяти, то есть `1.5e3` читается как 1,5 · 10³ = 1500.0, а `2.5E-4` — как 2,5 · 10⁻⁴ = 0.00025. Знак показателя пишется только для отрицательной степени, но `1.5e+3` тоже допустимо. Такая запись избавляет от подсчёта нулей в очень больших и очень малых величинах: `6.022e23` (число Авогадро) вместо двадцати трёх нулей, `9.11e-31` (масса электрона в килограммах) вместо тридцати.

Правила записи экспоненциальной формы:

- показатель — всегда целое число, дробным он быть не может; `3e` — ошибка компиляции `exponent has no digits`;
- при наличии показателя точка не обязательна: `3e2` — это `300.0` типа `double`, а не целое число;
- опускать часть числа можно и здесь: `.5e1` (равно 5) и `5.e1` (равно 50) — корректные литералы;
- тип определяется так же, как и в записи с точкой: `1.5e3` — `double`, `1.5e3f` — `float` (8 и 4 байта соответственно).

> [!warning] Пропуск
> Выноска «Литерала из одно…» и начало раздела о расширенных вещественных типах на снимках обрезаны. Дозаписать с новых фотографий.

…литералов для них: `f16` / `F16`, `f32` / `F32`, `f64` / `F64`, `f128` / `F128`, `bf16` / `BF16`. Например, `1.5f32` — литерал типа `std::float32_t`.

### Разделитель разрядов

Длинные числа трудно читать: в записи `1000000` разряды приходится пересчитывать глазами. Начиная с C++14 разряды целочисленного литерала (и литерала с плавающей точкой) разрешено группировать **апострофом** — этот приём называется разделителем разрядов (digit separator). Это чисто визуальный разделитель: компилятор его отбрасывает, на тип и значение литерала он не влияет, а группировать разряды можно как удобно — по три цифры, тетрадами, байтами:

- `1'000'000` — то же число, что и `1000000`;
- `0b0010'1010` — двоичный литерал по тетрадам;
- `0xFF'80'00` — шестнадцатеричный по байтам;
- `3.141'592'653` — работает и в литералах с плавающей точкой.

Ограничение одно: апостроф должен стоять **между цифрами** — записи `'42`, `42'` и `0x'2a` некорректны. Не путайте разделитель с символьным литералом: `'4'` — это символ, а `1'4` — число четырнадцать.

### Строковые литералы

**Арифметические литералы** не хранятся в памяти данных — они встраиваются прямо в машинные команды объектного кода.

**Строковые литералы** — другое дело. Строковый литерал в стиле C — это самостоятельный константный объект: массив типа `const char[N]` из символов литерала и завершающего нулевого символа `'\0'` (отсюда `N` на единицу больше, чем видимых символов). Такие объекты имеют статическую длительность хранения: они создаются до начала выполнения функции `main` и гарантированно существуют до самого конца работы программы — поэтому адрес строкового литерала можно без опаски хранить в указателе и возвращать из функции. Размещаются они обычно в отдельном пуле литералов ([[#1.1.2.3 (доп.) Пул литералов]]), доступном только для чтения; одинаковые строковые литералы компилятор может объединить в один экземпляр (зависит от опций компиляции).

Из константности следуют два практических вывода: строковый литерал можно присвоить только указателю `const char* ptr`, но не `char* ptr` (в C++11 такое преобразование стало ошибкой), а попытка изменить символ литерала — неопределённое поведение, на практике чаще всего аварийное завершение программы. Подробно об этом — в теме 2.5 «Типы строк в C++ и организация ввода-вывода».

> [!info] Склейка соседних строковых литералов
> Соседние строковые литералы склеиваются: записанные подряд `"foo" "bar"` — это ровно то же самое, что `"foobar"`. Подробно — в теме 2.5 «Типы строк в C++ и организация ввода-вывода».

### Пользовательские литералы (C++11)

C++ позволяет определять собственные суффиксы литералов — например, чтобы запись `42kg` создавала значение типа «масса». Пользовательские литералы бывают двух видов: «сырые» (raw) и «приготовленные» (cooked, для встроенных типов). Ограничение: создавать можно только литералы-суффиксы — собственный префикс (наподобие `0x`) определить нельзя. Подробности: <https://cppreference.com/cpp/language/user_literal>

Суффикс определяется функцией-оператором `operator""`. Например, так запись `1.5_kg` начинает означать массу в килограммах, а `300.0_g` — ту же массу в граммах.

> [!example] Пример 1.20 — Собственные суффиксы литералов `_kg` и `_g`
> ```cpp
> #include <iostream>
>
> // «приготовленные» (cooked) литералы: суффиксы _kg и _g хранят массу в килограммах
> constexpr double operator""_kg(long double value)
> {
>     return static_cast<double>(value);
> }
>
> constexpr double operator""_g(long double value)
> {
>     return static_cast<double>(value) / 1000.0;
> }
>
> int main()
> {
>     double load = 1.5_kg + 300.0_g;   // 1.8 — единицы согласованы записью, а не комментарием
>     std::cout << load << " кг\n";
>     return 0;
> }
> ```

Два правила, о которых легко забыть:

- собственный суффикс обязан начинаться с подчёркивания (`_kg`): суффиксы без подчёркивания зарезервированы за стандартной библиотекой;

## 1.1.2.3 (доп.) Пул литералов

Рассмотрим что такое пул литералов, как значение попадает туда и что с ним делает программа во время работы.

> [!abstract] Пул литералов (literal pool, string pool)
> область неизменяемых данных программы, куда компилятор складывает значения литералов, не помещающиеся в машинную команду — прежде всего строковые. Пул формируется на этапе компиляции, попадает в исполняемый файл и отображается в память при запуске программы.

### Что в пул попадает, а что нет

Арифметический литерал обычно **не** требует отдельной ячейки: значение `42` встраивается прямо в машинную команду как непосредственный операнд (immediate). Крупные константы — например, `double` — компилятор часто кладёт в константную секцию и обращается к ним по адресу, но не всегда: на ARM64 такое значение нередко собирается прямо инструкциями, без обращения к памяти.

Строковый литерал так встроить нельзя: это не число, а последовательность байтов, у которой есть адрес. Поэтому строковый литерал всегда становится объектом — массивом `const char[N]` со статической длительностью хранения, а в коде остаётся только его адрес.

### Путь литерала от исходника до памяти

> [!warning] Пропуск
> Нумерованный список «1. Компиляция. Компилятор складывает…» на снимках обрезан. Дозаписать с новых фотографий.

Литерал-источник при этом остаётся в пуле нетронутым: `arr` инициализируется копированием байтов.

### Одинаковые литералы могут склеиваться

Два одинаковых литерала компилятор вправе разместить в одной ячейке — экономия памяти на повторяющихся строках. Проверка на связке Apple clang 21 (`-O0`):

```cpp
const char* a = "Hello";
const char* b = "Hello";
const char* c = "World";
// a == b → true (один и тот же адрес)
// a = 0x100e2d1c1, b = 0x100e2d1c1, c = 0x100e2d1c7
```

Это **разрешение, а не обязанность**: стандарт оставляет вопрос на усмотрение реализации (влияют опции вроде `-fmerge-constants` у GCC и Clang, `/GF` у MSVC), а общий хвост (`"Hello"` и `"llo"`) на проверенной связке не разделяется вовсе.

### Как посмотреть пул своими глазами

Пул — не абстракция, его содержимое видно в готовом исполняемом файле:

```bash
strings -a program | head            # все текстовые строки файла
otool -s __TEXT __cstring program    # macOS: секция строковых литералов
objdump -s -j .rodata program        # Linux: то же для ELF
```

В дампе видно и то, что рядом со «своими» строками лежат литералы, попавшие из библиотек, и что байты идут подряд, разделённые нулями. Ещё нагляднее — Compiler Explorer (godbolt.org): в ассемблерном листинге литерал виден как метка в секции `.rodata`, а в коде на её месте стоит загрузка адреса.
