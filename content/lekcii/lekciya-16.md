## 1.4.8 Защита от повторного включения заголовочного файла (продолжение)

> [!quote] Документация по теме
> - `#include`: https://cppreference.com/cpp/preprocessor/include
> - Условная компиляция: https://cppreference.com/cpp/preprocessor/conditional

Директива `#include` вставляет содержимое заголовочного файла в точку включения (см. [[lekciya-14#1.4.7 Многофайловые проекты. Модульное программирование|1.4.7]]). Если один и тот же заголовок попадает в файл `.cpp` дважды, его содержимое окажется в единице трансляции два раза. Чаще всего так случается не из-за небрежности, а **транзитивно**: заголовок подключается ещё и через другой заголовок.

> [!example] Пример 1.79 — Повторное включение через другой заголовок
> Заголовок `point.hpp` определяет структуру, заголовок `geometry.hpp` подключает `point.hpp`, а `main.cpp` подключает оба:
>
> ```cpp
> // point.hpp
> struct Point
> {
>     // TODO: окончание примера на фото не попало
> ```

Страж включения и принцип его работы — см. [[lekciya-15#Страж включения|Лекцию 15]]. Общий вид стража:

> [!example] Сниппет 1.43 — Страж включения
> ```cpp
> #ifndef MODULE_HPP
> #define MODULE_HPP
>
> // объявления модуля
>
> #endif // MODULE_HPP
> ```

### Директива `#pragma once`

Ту же задачу одной строкой решает директива `#pragma once` в начале заголовочного файла:

```cpp
// point.hpp
#pragma once

struct Point
{
    double x;
    double y;
};
```

### Сравнение `#pragma once` и классических стражей

В современной разработке на C++ использование **только `#pragma once`** стало широко распространённой практикой: эту директиву вставляет Visual Studio при создании заголовочного файла, её используют многие открытые проекты, в том числе библиотека spdlog. Вместе с тем крупные проекты и руководства по стилю — Google, LLVM, Qt (для заголовков библиотеки), Chromium, а также библиотеки fmt, Catch2 и Boost — используют классические стражи:

- **Google.** В Google C++ Style Guide раздел «The #define Guard» требует: «All header files should have #define guards to prevent multiple inclusion»; имя стража строится из пути к файлу: `<PROJECT>_<PATH>_<FILE>_H_`. Раздел «Windows Code» прямо запрещает `#pragma once`.
- **LLVM.** В LLVM Coding Standards раздел «Self-contained Headers» требует, чтобы заголовок имел страж и сам подключал всё необходимое («a header should have header guards and include all other headers it needs»); раздел «Header Guard» задаёт имя стража: путь, по которому заголовок подключают, заглавными буквами (`llvm/Analysis/Utils/Local.h` → `LLVM_ANALYSIS_UTILS_LOCAL_H`). О `#pragma once` в документе не говорится.
- **Qt.** В Qt Coding Conventions раздел «Include guards» требует классические стражи в публичных и внутренних заголовках библиотеки («always use conventional include guards in public and private library headers»), имя — по имени файла (`QCLASSNAME_H`). ### Позиция C++ Core Guidelines

В C++ Core Guidelines (руководство, которое редактируют Б. Страуструп и Г. Саттер) правило **SF.8** называется «Use #include guards for all header files» — используйте стражи во всех заголовочных файлах. Примечание к правилу объясняет, почему не `#pragma once`: директива «is not standard and it is not portable. It injects the hosting machine's filesystem semantics into your program, in addition to locking you down to a vendor» — она не входит в стандарт, непереносима, привносит в программу особенности файловой системы машины, на которой идёт сборка, и привязывает код к поставщику компилятора.

Причин, таким образом, две: `#pragma once` — расширение компилятора, а не часть стандарта, и она узнаёт файл по его расположению на диске, поэтому зависит от файловой системы (символические ссылки, копии заголовка, сетевые диски). Классические стражи в стандарте отдельно не описаны: это приём, собранный из стандартных директив `#ifndef`, `#define` и `#endif`.

То же правило SF.8 требует, чтобы имя стража было уникальным: «do not just name the guard after the filename» — не называть страж только по имени файла, а добавлять имя библиотеки или компонента, например `LIBRARY_FOOBAR_H` для `foobar.h`.

В перспективе и стражи, и `#pragma once` должны заменить модули C++20 (`import` / `export`): модуль компилируется один раз и не подключается текстуально, поэтому проблема повторного включения для него не возникает <!-- TODO: продолжение на фото обрезано -->

### Как `#include` соединяет файлы проекта

```

─────────────                     ────────────                              ──────────                ──────────
include/add.hpp                   находит файл add.hpp
  int add(int x, int y);  ──────► (папка файла, затем -I include)
                                  и вставляет его текст
                                  вместо директивы #include
                                         │

Тот же проект соберём компилятором MSVC в командной строке разработчика (см. [[lekciya-15#1.4.6.3 Компилятор MSVC (Microsoft Visual C++)|1.4.6.3 Компилятор MSVC]]). Чтобы скомпилировать программу с дополнительными файлами исходного кода, введите их все в командной строке (рисунок 1.11):

**Рисунок 1.11 — Компиляция многомодульного проекта** (снимок Developer Command Prompt for VS 2022)

Опции `/std:c++20`, `/W4` и `/EHsc` — те же, что для однофайловой программы (см. 1.4.6.3).

При указании дополнительных исходных файлов компилятор использует первый входной файл для создания имени программы. В этом случае выводится программа с именем `sumsub.exe`. Чтобы изменить имя, например, на `program.exe`, добавьте опцию `/Fe:`:

```
D:\sumsub>cl /std:c++20 /W4 /EHsc sumsub.cpp arithmetic.cpp io.cpp /Fe:program.exe
```

### Компиляция и компоновка по шагам

Команда `g++ sumsub.cpp arithmetic.cpp io.cpp -o sumsub.exe` за один вызов выполняет для каждого файла `.cpp` препроцессинг, компиляцию и ассемблирование, а затем компонует полученные объектные файлы. Эти шаги можно выполнить по отдельности. Напомним, что опция `-c` (у MSVC — `/c`) останавливает драйвер компилятора после создания объектного файла (без компоновки), см. [[lekciya-15#1.4.3 Этапы сборки программы на C++ (продолжение)|1.4.3 Этапы сборки программы]]:

```bash
g++ -std=c++20 -Wall -Wextra -c sumsub.cpp       # sumsub.o
g++ -std=c++20 -Wall -Wextra -c arithmetic.cpp   # arithmetic.o
g++ -std=c++20 -Wall -Wextra -c io.cpp           # io.o
g++ sumsub.o arithmetic.o io.o -o sumsub.exe     # компоновка
```

```
cl /std:c++20 /W4 /EHsc /c sumsub.cpp arithmetic.cpp io.cpp   # sumsub.obj, arithmetic.obj, io.obj
cl sumsub.obj arithmetic.obj io.obj /Fe:sumsub.exe            # компоновка
```

Каждый файл `.cpp` компилируется независимо от остальных: компилятору достаточно объявлений из заголовочных файлов, а определения функций других модулей ему не нужны. Сопоставить вызов `sum(a, b)` в `sumsub.o` с определением `sum` в `arithmetic.o` — задача компоновщика.

> [!abstract] Раздельная компиляция (separate compilation)
> сборка программы, при которой каждый исходный файл `.cpp` компилируется в объектный файл независимо от остальных, а затем компоновщик объединяет объектные файлы в исполняемый файл.

Раздельная компиляция экономит время: после правки одного файла перекомпилировать нужно только его, а остальные объектные файлы используются повторно. Именно так работают системы сборки — CMake и среды разработки следят, какие файлы изменились (см. 4.1.2 «Сборка проекта с помощью CMake»). В лабораторных работах проект собирается готовым `CMakeLists.txt` (см. 1.4.10 «Структура учебного проекта»), а команды по шагам выполняют один раз — чтобы увидеть, из чего складывается сборка.

### 1.5.1 Понятие модуля — пара файлов и модуль C++20

> [!quote] Документация и стандарт по теме
> - Документация: https://cppreference.com/cpp/language/modules
> - Стандарт: https://eel.is/c++draft/module

Слово «модуль» в C++ употребляется в двух разных смыслах, и их нужно различать: в литературе, документации и сообщениях компиляторов встречаются оба.

#### Модуль как пара файлов

В модульном программировании модулем называют логическую пару из заголовочного файла (`*.hpp`) и файла реализации (`*.cpp`) — именно так мы раскладывали программу по файлам в теме 1.4 (см. 1.4.7). Такой **модуль — соглашение об организации кода, а не конструкция языка**: компилятор ничего не знает о том, что `add.hpp` и `add.cpp` составляют одно целое. Связывает их препроцессор директивой `#include`, которая текстуально вставляет заголовок в каждый файл, где он нужен. Поэтому такому модулю нужен страж включения (см. 1.4.8), а заголовок компилируется заново в каждой единице трансляции, которая его подключает.

#### Модуль C++20

Начиная со стандарта C++20 в язык добавлено понятие «модуль» — конструкция языка, которую обрабатывает компилятор, и добавлены ключевые слова `module`, `export` и `import`.

> [!abstract] Модуль C++20 (module)
> именованная единица программы, объявляемая в исходном файле строкой `export module имя;`: модуль сам указывает, какие объявления он экспортирует (ключевым словом `export`), а другие файлы подключают его объявлением `import имя;`.

Для модулей служат три слова — `module`, `export` и `import`. Из них составляются такие конструкции:

- `export module имя;` — объявляет модуль `имя`; это первая строка файла интерфейса модуля (основной единицы интерфейса);
- `module имя;` — без `export`: первая строка единицы реализации модуля `имя` (см. Сниппет 1.49 ниже);
- `module;` — начало глобального фрагмента модуля: между этой строкой и объявлением модуля заголовки подключают директивой `#include` (см. 1.5.2 «Модули C++20 — сборка программы»);
- `export` перед объявлением — делает объявление видимым в файлах, которые импортируют модуль; объявление без `export` остаётся внутренним делом модуля;
- `import имя;` — подключает модуль `имя`; это объявление языка, а не директива препроцессора, поэтому в конце стоит точка с запятой.

Слова `module` и `import` — контекстно-зависимые ключевые слова: особый смысл они имеют только в этих конструкциях, а в остальной программе это обычные имена. `export` — ключевое слово, зарезервированное ещё в C++98; в C++20 оно получило новый смысл (см. [[lekciya-08|1.1.2.3 Имена — идентификаторы и ключевые слова]]).

> [!example] Сниппет 1.48 — Модуль C++20: файл интерфейса и импорт
> Файл `rectangle.cppm`:
> ```cpp
> export module rectangle; // объявление модуля rectangle
>
> // export: функция видна файлам, которые импортируют модуль
> export double area(double width, double length)
> {
>     return width * length;
> }
> ```
> Файл `main.cpp`:
> ```cpp
> #include <iostream>
> import rectangle; // объявление языка, а не директива препроцессора: в конце «;»
>
> int main()
> {
>     constexpr double ROOM_WIDTH = 3.0;
>     constexpr double ROOM_LENGTH = 4.5;
>     std::cout << area(ROOM_WIDTH, ROOM_LENGTH) << '\n'; // 13.5
> }
> ```

> [!tip] Расширение файла интерфейса
> На доске: у g++ и Clang — `.cppm`, у MSVC — `.ixx`.

Как собирается программа с модулем (Пример 1.82):

```
Файлы проекта
─────────────
arithmetic.cppm                                         1. Компиляция интерфейса модуля
  export module arithmetic;                    ──────►     (выполняется первой)
  export namespace arithmetic {                                │
      int sum(int a, int b) { … }                              ├──► arithmetic.o   (определения sum, sub)
      int sub(int a, int b) { … }                              └──► arithmetic.pcm (BMI: экспортированные объявления
  }                                                                  sum, sub; GCC — .gcm, MSVC — .ifc)
                                                                          │ читает компилятор
main.cpp                                                                  ▼
  #include <iostream>                          ──────►  2. Компиляция main.cpp
  import arithmetic;                                       #include <iostream> — препроцессор вставляет текст заголовка;
  int main() { … arithmetic::sum(…) … }                    import arithmetic; — компилятор читает готовый BMI
                                                               └──► main.o (вызовы sum, sub — адреса неизвестны)

arithmetic.o + main.o ──► 3. Компоновщик связывает вызовы с определениями по именам функций ──► app (исполняемый файл)
```

**Рисунок 1.12 — Сборка программы с модулем C++20**

> [!note]
> BMI нужен только компилятору: без `arithmetic.pcm` нельзя скомпилировать `main.cpp`, поэтому интерфейс модуля компилируют первым. Компоновщику нужны только объектные файлы, а при выполнении модуль не отличается от остального кода программы.

| | (а) Модуль как пара файлов | (б) Модуль C++20 |

### 1.6.1 Область видимости

> [!quote] Документация и стандарт по теме
> - Область видимости: https://cppreference.com/cpp/language/scope · стандарт: https://eel.is/c++draft/basic.scope
> - Неквалифицированный поиск имён: https://cppreference.com/cpp/language/unqualified_lookup · стандарт: https://eel.is/c++draft/basic.lookup.unqual

> [!abstract] Область видимости (scope)
> часть текста программы, в пределах которой имя (идентификатор) можно использовать для обращения к обозначенной им сущности — переменной, функции, типу [14, п. 8.4].

Область видимости — свойство имени, а не объекта: она говорит, где в тексте программы имя можно написать, а не сколько времени существует то, что оно обозначает (время жизни — см. ниже).

Как правило, область видимости ограничивается блоком кода, который заключается в фигурные скобки (см. 1.2.4 «Составная инструкция»).

Каждое имя объявляется в своей области видимости и является действительным (т. е. находится в области видимости), начиная с точки объявления и заканчивая концом области видимости, в которой оно объявлено.

> [!important] Видимость во вложенных областях
> Имена, принадлежащие области видимости, видны из вложенных в неё других областей видимости. Если во вложенной области объявлено такое же имя, оно скрывает внешнее.

Основное предназначение области видимости — сохранить локальность имён, чтобы они не пересекались с именами, объявленными в другом месте.

Помните: реальные программы содержат многие тысячи именованных сущностей. Для возможности поддержки и сопровождения таких программ большинство имён должны быть локальными <!-- TODO: продолжение на фото обрезано -->

#### Как компилятор находит имя

Встретив **неквалифицированное** имя — имя без `::` перед ним, — компилятор ищет его объявление, начиная с самой внутренней области видимости, в которой стоит имя, и переходя к объемлющим — вплоть до глобальной. Поиск останавливается на первой области, где объявление нашлось; поэтому внутреннее имя скрывает одноимённое внешнее. В блоках и пространствах имён учитываются только объявления, расположенные выше точки использования: имя, объявленное ниже, ещё не видно.

Из этого правила следует, почему функцию, определённую ниже `main`, нельзя вызвать из `main` без прототипа: в точке вызова её имя ещё не объявлено (см. [[lekciya-03|1.1.1.4 Базовое понятие функции и проверка работы функции]]).

#### Разновидности областей видимости

Разновидности областей видимости, которые можно использовать для управления используемыми именами:

1. **Глобальная область видимости (global scope)** — область исходного текста, не входящая ни в одну другую область видимости. Имена, объявленные вне всех функций и пространств имён, видны от точки объявления до конца единицы трансляции — файла `.cpp` вместе со всеми подключёнными в него заголовками (см. [[lekciya-15#1.4.5.1 Трансляция программы|1.4.5.1 Трансляция программы]]).
2. **Область видимости пространства имён (namespace scope)** — именованная область видимости, вложенная в глобальную область видимости или в другое пространство имён (см. 1.6.2). Строго говоря, глобальная область видимости — тоже область пространства имён: глобального.
3. **Блочная (локальная) область видимости (block scope)** — между фигурными скобками `{ ... }` блока. Параметры функции видны во всём её теле; объявить в самом внешнем блоке функции локальную переменную с именем параметра нельзя — это ошибка повторного объявления (`redefinition of 'value'`).
4. **Область видимости инструкции** — имена, объявленные в заголовке инструкций `for`, `if`, `while` или `switch` (например, счётчик цикла `for (int i = 0; …)`), видны только в этой инструкции — до конца её тела, а у `if` — и в ветви `else`. Название учебное: стандарт не выделяет такую область отдельно, но правило именно такое.
5. **Область видимости перечисления (enumeration scope)** <!-- TODO: продолжение списка на фото не попало -->

#### Область видимости и многофайловая программа

Глобальная область видимости ограничена единицей трансляции. Функция, определённая в `a.cpp`, в `b.cpp` не видна: компилятор обрабатывает каждый файл `.cpp` отдельно, и вызов без объявления в `b.cpp` — ошибка `use of undeclared identifier`. Чтобы имя стало видно, в `b.cpp` должно оказаться его объявление — для этого объявления и выносят в заголовочный файл и подключают его директивой `#include` (см. 1.4.7). А то, что объявление в одном файле и определение в другом обозначают одну и ту же функцию, обеспечивает связывание (linkage) — тема 3.5 (3.5.3 «Время жизни и связывание»).

#### `::` — оператор разрешения области видимости

Оператор разрешения области видимости `::` (scope resolution operator) указывает, в какой области искать имя:

1. `пространство_имён::имя` — имя из указанного пространства имён: `std::cout`, `stats::count`. Так различают одинаковые имена из разных пространств имён.
2. `::имя` — имя из глобальной области видимости, даже если в текущем блоке есть локальная переменная с таким же именем.

#### Квалифицированное и неквалифицированное имя

Имя без `::` перед ним — например, `cout` или `area` — называют **неквалифицированным**; компилятор ищет его по правилу из 1.6.1.

> [!abstract] Квалифицированное (полное) имя (qualified name)
> имя, перед которым через `::` указано, где его искать: пространство имён (`std::cout`, `geometry::area`), а в дальнейшем также класс или перечисление (`Color::Red`).

Обратиться к имени из пространства имён можно тремя способами:

1. по квалифицированному имени: `geometry::area(3.0, 4.5)`, `std::cout`;
2. using-объявлением: `using std::cout;` — после него одно имя `cout` доступно без квалификации;
3. using-директивой: `using namespace std;` — после неё без квалификации доступны все имена пространства имён `std`.

Второй и третий способы сокращают запись, но имеют свои ловушки; они разбираются в 1.6.3. Квалифицированное имя — самый надёжный способ: из записи видно, откуда взято имя, и совпадений не возникает.

#### Пространство имён std

`std` — пространство имён стандартной библиотеки C++: все её средства (`std::cout`, `std::string`, `std::vector` и т. д.) объявлены внутри него. Каждый стандартный заголовок (`<iostream>`, `<string>`, …) добавляет в `std` свою часть объявлений. Заголовки, унаследованные от языка C (`<cmath>`, `<cstdint>`), помещают имена в `std` и могут также помещать их в глобальное пространство имён, но это не гарантировано — переносимо обращаться к ним через `std::`: `std::sqrt`, `std::int32_t`.

> [!danger] Не добавляйте свои объявления в `std`
> Пространство имён `std` принадлежит стандартной библиотеке. Если программа добавляет в него (или во вложенное в него пространство имён) свои объявления или определения, её поведение не определено — за немногими исключениями, которые задаёт сам стандарт, например разрешёнными специализациями шаблонов стандартной библиотеки ([namespace.std], https://eel.is/c++draft/namespace.std; о неопределённом поведении — 2.2.3.4 «Неопределённое поведение (UB)»). Свои функции и типы размещайте в собственных пространствах имён.

### 1.6.3 Ключевое слово using

> [!quote] Документация и стандарт по теме
> - using-директивы: https://cppreference.com/cpp/language/namespace · стандарт: https://eel.is/c++draft/namespace.udir
> - using-объявление: https://cppreference.com/cpp/language/using_declaration · стандарт: https://eel.is/c++draft/namespace.udecl
> - Псевдонимы типов: https://cppreference.com/cpp/language/type_alias · стандарт (`typedef`, `using`): https://eel.is/c++draft/dcl.typedef

Квалифицированное имя надёжно, но длинно. Ключевое слово `using` сокращает запись: оно даёт второй и третий способы обратиться к имени из пространства имён — using-объявление и using-директиву (первый способ, квалифицированное имя, — в 1.6.2). Кроме того, `using` объявляет псевдонимы типов.

#### using-объявление

> [!abstract] using-объявление (using-declaration)
> объявление вида `using пространство_имён::имя;`, которое вводит в область видимости одно имя из пространства имён. Далее это имя можно использовать без квалификации.

```cpp
using std::cout;
cout << "Hello!";
```

using-объявление действует до конца области видимости, в которой записано: внутри функции — до конца функции, на уровне файла — до конца единицы трансляции. Остальные имена из `std` по-прежнему пишут с префиксом `std::`.

#### using-директива

> [!abstract] using-директива (using-directive)
> объявление вида `using namespace имя;`, которое делает доступными без квалификации сразу все имена указанного пространства имён.

Несмотря на название, using-директива — не директива препроцессора (как `#include`, см. [[lekciya-15#1.4.3.1 Препроцессинг|1.4.3.1 Препроцессинг]]): её обрабатывает компилятор, и она, как любое объявление, заканчивается точкой с запятой. Директива — только та форма `using`, в которой есть слово `namespace`.

```cpp
using namespace std;
cout << "Hello!";
```

Директива удобна, когда из пространства имён нужно много имён, но она приносит в область видимости **все** его имена — в том числе те, о существовании которых программист не знает. Если одно из них совпадёт с именем программы, обращение к этому имени станет неоднозначным.

#### Псевдонимы типов

Ещё одно применение `using` не связано с пространствами имён: объявление `using имя = тип;` вводит **псевдоним типа** — другое имя для уже существующего типа. Псевдоним сокращает длинные имена типов и подсказывает их смысл.

> [!example] Сниппет 1.54 — Псевдоним типа
> ```cpp
> #include <iostream>
>
> using ullong = unsigned long long; // псевдоним типа (C++11)
> // typedef unsigned long long ullong; // то же в старом стиле языка C
>
> int main()
> {
>     constexpr ullong WORLD_POPULATION = 8'100'000'000;
>     unsigned long long copy = WORLD_POPULATION; // тот же тип: преобразования нет
>     std::cout << copy << '\n';
> }
> ```
> `ullong` и `unsigned long long` — один и тот же тип: значение передаётся между ними без преобразования. Псевдоним не создаёт новый тип.

Тот же псевдоним можно объявить в старом стиле языка C ключевым словом `typedef`: `typedef unsigned long long ullong;`. В новом коде предпочитают `using` (C++ Core Guidelines T.43): запись «имя = тип» читается слева направо, как присваивание, а шаблон псевдонима — например, `template<typename T> using Vec = std::vector<T>;` — через `typedef` объявить нельзя (подробнее — в [[lekciya-19#3.4.2.9 Шаблон псевдонима|3.4.2.9 Шаблон псевдонима]]).

У `using` есть и другие применения, например `using enum` (C++20) для значений перечисления — см. тему 3.2.
